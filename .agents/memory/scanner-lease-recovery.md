---
name: Scanner lease recovery
description: Discovery-scanner recovery when a lease cannot be released during a database outage.
---

Discovery scanner ownership is a dedicated `discovery-scanner` lease, separate from the shared `market-cycle` lease used by watcher and optional background work. A database outage that prevents either lease from being released leaves its row valid until TTL expiry, but a background release failure must never prevent a new discovery cycle. A scanner release failure is not a successful scan: persist its reason and expected expiry in order once the database returns, and preserve that expiry across ordinary scanner-contention retries. Treat an unavailable control-plane as a distinct recovery state: retry one terminated heartbeat connection through the dedicated scheduler pool, but preserve definitive lease loss as a guard-cancellation boundary rather than immediately crash-looping the worker.

**Why:** A production outage left a watcher/background `market-cycle` row valid after its owner could not delete it, repeatedly deferring new-signal discovery. A local hard timeout can also leave abort-ignoring scanner work unwinding after the scanner lease TTL; lease expiry alone then cannot prevent an overlapping in-process scan. Later production evidence showed the same amplification on `discovery-scanner`: a 5-second release timeout left its 30-minute row valid, so the scanner repeatedly saw `lease_busy` despite completing no long market computation. Application-level `Promise.race` timeouts do not cancel the underlying PostgreSQL request, so retries can still exhaust the small process pool.

**How to apply:** Keep discovery lease ownership as the cross-worker source of truth for scanner watchdog activity; never infer scanner activity from a background `market-cycle` row. Watchdog lease-status reads are themselves control-plane reads, so they must fall back to the explicit control-plane-recovery state instead of aborting the report tick. Preserve no-overlap with a local settlement fence after any hard timeout. If it survives its short grace period, restart the worker at the process boundary rather than clearing the fence in-process. Treat a start timestamp, a successful completion, and a recoverable failure as separate persisted facts; never refresh the successful-completion clock merely because an attempt began or was force-reset. A live discovery lease takes precedence over historical release-failure metadata in watchdog state. Size the discovery lease TTL and heartbeat for recovery, not only safety: a transient release failure must not cost an entire scan interval. Give lease traffic its own one-connection pool with PostgreSQL-enforced statement deadlines, and never retry a caller-timed-out operation whose original request can still be in flight. Protect non-critical work by deferring it as soon as the ordinary pool reports pressure or control-plane recovery begins; keep actual position protection outside that gate.
**Release retry and TTL cap (2026-10-21):** release is retried 3× inline (0.5 s, 1.5 s pauses) and then in the background every 5 s until the lease deadline; the delete is owner-token scoped, so repeating it is safe. Default lease TTL is 3 min with a 30 s heartbeat, and no caller may exceed 5 min. Production deployment logs for the old process (before the 05:57 publish) were not retained, so the 04:14 release error text is unknown; discovery lease TTL was already 90 s since August, so it cannot explain a 64-minute hold on its own.
**Why:** the owner saw the scanner stall 04:14–05:58 with `lease_release_failed`.
**How to apply:** when diagnosing a lease stall, first check that logs exist for the window; do not assume the TTL was the cause.
