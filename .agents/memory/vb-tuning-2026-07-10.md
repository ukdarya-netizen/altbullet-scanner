Context: 2026-07-04 tightening of volume_breakout gates drove fire rate to
quiet=0, mover=2, spot=24 over 14 days. User supplied a tuning doc; changes
implemented:

- Gate 3b (spot-vol confirmation, shared by quiet/mover): threshold split by
  sub-pattern instead of one shared `spotMult < 1.3` literal — quiet now 1.1,
  mover now 1.2 (both still OR'd with `volMult >= 8.0` escape hatch).
- Mover OI floor: was a hard reject at `oiChange30m < -2.0`. Now OI >= -2%
  always passes; below that, added a funding-rate short-squeeze exception
  (`getFundingRate` from bingx.ts, reject unless `lastFundingRate < -0.0001`).
- volume_breakout_spot OI-all-TF gate: was "all 4 TFs (5m/30m/1h/4h) strictly
  positive or reject" — this was ~72% of rejections from ordinary short-TF
  noise. Now allows at most one TF to be non-positive, and only down to a
  soft floor of -0.5%; two or more negative TFs, or any TF below -0.5%, still
  rejects. Missing data on any TF is still a hard reject (unchanged).
- quiet CVD gate: behavior was already a hard reject when no CVD data at all
  (comment incorrectly called it "soft"); comment corrected and a
  `_pdbReject(..., "cvd_no_data")` call added so it shows up in
  pattern_debug_log metrics instead of being invisible.

**Why:** the fire-rate collapse was multiple independently-strict gates each
selecting for the same feature (positive OI everywhere, strong spot response) —
softening one alone wasn't going to fix it; needed simultaneous relaxation
across gates.

**How to apply:** if a next round of tuning is needed, re-pull
pattern_debug_log rejection-reason breakdowns first (same method as before) to
confirm which gate is now the dominant blocker before changing more
thresholds.

**Dead pattern cleanup (same day):** `volume_breakout_futures` sentimentKey
was fully removed from the codebase (type union, docs, labels, badge colors,
legacy-compat checks in scanner.ts/telegram.ts/watcher.ts) — it was a stale
label left over from when the pattern was renamed/split into quiet/mover;
0 live DB rows had it in prod. Lesson: when doing an "audit dead code" pass,
grep every SentimentKey string across api-server AND alpha-scanner (frontend
mirrors pattern-labels.ts independently) — a legacy key can hide in type
unions and UI color maps even after its detection logic is gone.

## Legacy pattern still visible in Analysis page despite removal from ACTIVE lists
`analysis.tsx` (Анализ page) has its own separate `ACTIVE_PATTERNS` list + a "legacy row" mechanism that surfaces ANY pattern found in DB but not in that list as a dimmed extra row — this is how a fully-removed pattern (`volume_breakout_futures`) kept reappearing with real historical data even after being purged from dashboard.tsx/signals.tsx/pattern-labels.ts. Fixed by adding an explicit `DEAD_PATTERNS` exclusion array filtered out of `allRows` before render. Any future pattern removal must also update analysis.tsx's `ACTIVE_PATTERNS` + `DEAD_PATTERNS`, not just the other 3 files.
