Renamed `finalAlphaScore` → `bulletScore` and `calcAlphaScore` → `calcBulletScore` **only inside** `scanner.ts` / `scanner-patterns.ts` (matches the "Bullet Score" label users see in Telegram). By explicit user decision, the DB column (`alpha_score`), OpenAPI/Zod contract, and frontend still use `alphaScore` — a full rename across those layers was deferred as a separate task (needs a DB migration + codegen regen, not worth the risk for a cosmetic rename alone).

The `if (bulletScore < 5) continue;` gate at the end of the pattern-detection pipeline (right before signal creation) was removed by user decision. Score is still computed and stored on every signal (visible in Telegram/DB) but no longer blocks a signal from being created — only the pattern's own gate conditions, cooldowns, and dedup still filter signals.

**Why:** user wants live data on how many signals from "dead" patterns (quiet_oi_accumulation, oi1h_breakout, spot_oi4h_build, bingx_exclusive, 4h_momentum, volume_taker, spot_momentum_reversal, spot_absorption, flush_reversal) were being silently killed by the score floor rather than by their own gate being wrong.

**How to apply:** when asked to compare "before vs after" fire rates for these patterns, filter `signals`/`pattern_debug_log` by `logged_at >= '2026-07-10'` (deploy date) — data before that date is gate-suppressed and not comparable 1:1. Note: the `passed_gate_scored` diagnostic (cvd_diag) enrichment in `diagPatternPassed` had ZERO rows in production over the prior 14 days despite being wired in code — worth re-checking if it's actually firing before relying on it for future gate-impact analysis.

**passed_gate_scored 0-rows root cause (resolved 2026-07-10):** confirmed via git history across "Published your App" commits that this enrichment first reached prod at 2026-07-09 16:53:58 UTC — only ~15h of runtime, not 14 days. Not a bug. Post-deploy SQL showed 36 `passed_gate` events (4h_momentum, bingx_exclusive, spot_absorption, quiet_oi_accumulation) but 0 `passed_gate_scored`/`signals` — the scoring event genuinely hadn't occurred yet for these low-frequency patterns. Cross-referencing `oi_watch`: quiet_oi_accumulation/spot_absorption route through the OI Watch confirming queue and can expire before price confirms; 4h_momentum/bingx_exclusive have 0 oi_watch rows, meaning they die earlier at the OI+Volume confirm-gate, before ever queuing. Lesson: check the deploy timeline of the *instrumentation itself* before assuming "0 rows" means a wiring bug.

**New durable diagnostics (2026-07-10):** `pushFilteredCandidate` (filtered-log.ts) now also persists every filtered/expired candidate to `missed_signals_log` (source='filtered_candidate') with a `pattern` field — durable across restarts, unlike the old in-memory 100-entry cap. Covers both requested bottlenecks using existing reject branches (already had oi/price/vol + reason label): the direct OI+Volume confirm-gate reject (`oi_filter`, tagged `pattern: "4h_momentum"|"bingx_exclusive"|null`) and the OI Watch expiry sweep (trend_broken/oi_drained/oi_faded/price_retrace/price_runaway/ghost_pump, tagged `pattern: entry.sentimentKey ?? entryTf`). Query `missed_signals_log WHERE source='filtered_candidate'` for the per-pattern breakdown once data accumulates.
